# ZOOMIX Commercial Studio — Product Vision

> وثيقة مرجعية تجمع القرارات والأفكار التي تمت مناقشتها بخصوص تطوير صفحة Studio إلى نظام تجاري متكامل لـ Zoomix.
>
> الحالة: تصور معتمد — بدأ تنفيذ الأساس التقني لقائمة الأسعار وعروض الأسعار.
> آخر تحديث: 8 أكتوبر 2026.

---

## 1. الملخص التنفيذي

الهدف ليس تحويل Studio إلى CRM عام أو لوحة Admin تقليدية، بل بناء نظام خاص بطبيعة عمل Zoomix يدير الرحلة التجارية كاملة:

```text
Brief
  → Lead
  → Pricing & Scope
  → Quote
  → Client Review
  → Acceptance / Revision
  → Contract & Deposit
  → Project
  → Payments & Profitability
```

الاسم الوظيفي المقترح للنظام:

> **ZOOMIX Commercial Studio — من الطلب إلى عرض السعر، ومن عرض السعر إلى التعاقد.**

أهم نقطة معمارية: يجب أن تصبح قاعدة الأسعار والباقات داخل Studio هي **المصدر المركزي الوحيد للحقيقة**. الموقع العام، ومنشئ عروض الأسعار، والخصومات، والتقارير تستخدم جميعها نفس البيانات.

## 2. الوضع الحالي في الموقع

الموقع يحتوي حاليًا على:

- 3 باقات تأسيس.
- 3 باقات صناعة محتوى.
- 3 باقات تغطية فعاليات.
- 3 باقات شراكة شهرية.
- 9 خدمات منفصلة.
- نموذج Brief يحفظ الباقة أو الخدمة والمسار والميزانية والمدة وبيانات العميل.
- Studio لعرض الطلبات، البحث، الفلاتر، الحالات والملاحظات.
- Cloudflare Worker وD1 لحفظ البيانات والجلسات.
- تحديث لحظي للطلبات داخل Studio.
- تصدير CSV ونسخة احتياطية JSON.

المشكلة الأساسية أن الباقات والأسعار والتفاصيل مكتوبة حاليًا داخل ملفات الكود. أي تعديل في السعر أو المحتوى يحتاج تعديلًا برمجيًا ورفع نسخة جديدة من الموقع.

## 3. نتائج دراسة السوق

### الأنماط المثبتة في المنتجات العالمية

الأدوات المتخصصة في عروض الأسعار وإدارة شركات الخدمات تطبق بصورة متكررة:

- كتالوج مركزي للمنتجات والخدمات والأسعار.
- عروض أسعار تفاعلية بدل الاعتماد على PDF ثابت فقط.
- باقات متعددة داخل نفس العرض.
- خدمات وإضافات اختيارية يحددها العميل.
- كميات وأسعار وخصومات محسوبة تلقائيًا.
- قواعد موافقة عند تجاوز نسبة خصم أو قيمة معينة.
- رابط خاص للعميل مع إمكانية القبول أو طلب تعديل.
- تحويل العرض المقبول إلى فاتورة أو مشروع.
- دفعة مقدمة وخطة دفعات.
- تاريخ انتهاء للعرض.
- نسخ وإصدارات للعروض.
- Client Portal في المراحل المتقدمة.

## 4. دمج الأفكار المتشابهة

بدل بناء عشرات الأقسام المنفصلة، يتم دمج جميع الأفكار في خمسة أنظمة رئيسية:

| النظام | الأفكار المندرجة تحته |
|---|---|
| Commercial Catalog | Price List Desk، إدارة الباقات، الخدمات، الإضافات، التكلفة، هامش الربح، قواعد التسعير والخصومات |
| Quote Studio | Quote Builder، Scope Builder، حاسبة التسعير، إصدارات العرض، التفاوض والموافقات |
| Client Deal Room | عرض العميل، PDF، القبول والرفض، طلب التعديل، العقد، الدفعات والملفات |
| Sales Control | Leads، Kanban، المتابعات، Lead Score، ابدأ يومي وTelegram |
| Business Intelligence | تقارير المبيعات، الربحية، المصادر، الخصومات، الباقات وأسباب الفوز والخسارة |

كل الأفكار السابقة محفوظة داخل هذه الأنظمة؛ الدمج هدفه منع التكرار وليس حذف الأفكار.

## 5. Commercial Catalog / Price List Desk

هو قلب النظام ومصدر الحقيقة الوحيد للأسعار.

### أنواع العناصر

- Packages.
- Services.
- Add-ons.
- Production expenses.
- Pricing rules.

### أمثلة للعناصر

- باقة Presence.
- Content Build.
- Event Signature.
- تصميم منشور.
- فيديو قصير.
- Landing Page.
- جلسة تصوير.
- فيديو إضافي.
- ساعة تصوير إضافية.
- مصور ثانٍ.
- انتقالات.
- معدات.
- تسليم سريع.
- مراجعة إضافية.

### بيانات كل عنصر

- معرف ثابت لا يتغير.
- الاسم العربي والإنجليزي.
- الوصف العربي والإنجليزي.
- الفئة.
- سعر البيع.
- التكلفة الداخلية.
- الحد الأدنى المسموح للسعر.
- وحدة الحساب.
- مدة التنفيذ.
- عدد المراجعات.
- البنود المشمولة.
- البنود المستبعدة.
- الباقات المرتبطة.
- هل يظهر على الموقع؟
- هل يمكن إضافته إلى عرض سعر؟
- هل هو اختياري أم إجباري؟
- تاريخ بدء السعر وانتهائه.
- Active / Draft / Archived.
- آخر تعديل ومن قام به.
- تاريخ نسخ الأسعار السابقة.

### قواعد مهمة

- تغيير السعر لا يغير العروض القديمة.
- كل عرض يحفظ Snapshot من الاسم والوصف والسعر وقت إرساله.
- الحذف يكون Archive في المعتاد وليس حذفًا نهائيًا.
- يوجد Preview قبل نشر أي تغيير على الموقع.
- يمكن حفظ التعديلات كمسودة قبل نشرها.
- يجب إظهار تحذير واضح يشرح ما الذي سيتأثر بالتغيير.

## 7. Quote Studio / Quote Builder

عند فتح أي Brief يظهر زر **إنشاء عرض سعر**، ويتم نقل بيانات العميل واختياراته تلقائيًا.

### أوضاع إنشاء العرض

#### Quick Quote

- اختيار باقة.
- تعديل بسيط للسعر.
- إضافة خصم.
- إرسال سريع.

#### Custom Quote

- إضافة وحذف بنود.
- تغيير الكميات والأسعار.
- إضافة بند مخصص.
- تحديد بنود اختيارية.
- تعديل المدة والمراجعات.
- إضافة تكاليف الإنتاج والمعدات والانتقالات.

#### Package Comparison

إرسال ثلاثة بدائل مثل:

- Essential.
- Recommended.
- Premium.

ويختار العميل البديل المناسب داخل صفحة العرض.

### وظائف منشئ العرض

- اختيار بنود من الكتالوج.
- إضافة بند يدوي.
- إعادة ترتيب البنود.
- تعديل الوصف داخل العرض دون تعديل الكتالوج.
- الكمية وسعر الوحدة.
- خصم على بند محدد.
- خصم على العرض بالكامل.
- ضريبة عند الحاجة.
- بند مجاني.
- إضافة اختيارية.
- إظهار أو إخفاء سعر بند مع إظهار الإجمالي.
- خطة الدفعات.
- مدة التنفيذ.
- عدد المراجعات.
- الاستثناءات والشروط.
- تاريخ صلاحية العرض.
- لغة العرض.
- ملاحظات العميل والملاحظات الداخلية.

### الحسابات التلقائية

```text
Subtotal
  - Item Discounts
  - Quote Discount
  + Tax
  + Expenses
  = Client Total
```

ويظهر داخليًا فقط:

- إجمالي التكلفة.
- الربح المتوقع.
- هامش الربح.
- الحد الأدنى المسموح.
- تحذير إذا كان العرض غير مربح.

### إصدارات العرض

- Version 1.
- Version 2 بعد التفاوض.
- Version 3 النهائية.
- الاحتفاظ بكل النسخ السابقة.
- تسجيل من عدّل ومتى.
- منع تعديل نسخة تم قبولها؛ يتم إنشاء إصدار جديد بدلًا منها.

- ملخص الاحتياج.
- نطاق العمل.

- الإضافات الاختيارية.

- خصم نسبة مئوية.

- خصم لعميل محدد.

### إعدادات العرض

- اسم العرض والكود.

- الباقات والخدمات المسموح بها.
- الحد الأدنى لقيمة الطلب.

## 28. ملاحظات تنفيذية يجب عدم نسيانها

- تفاصيل الباقات تظل ظاهرة ولا يتم اختصارها أو إخفاؤها.
- العربية والإنجليزية جزء من بنية البيانات وليستا إضافة لاحقة.
- كل سعر يستخدم أعدادًا صحيحة/وحدات نقدية في قاعدة البيانات، وليس نصًا منسقًا.
- كل عرض يحفظ Snapshot حتى لا يتغير تاريخيًا.
- الروابط العامة تستخدم Tokens آمنة وتنتهي أو يمكن إبطالها.
- الأسرار مثل Telegram Bot Token تحفظ في Cloudflare Secrets.
- الحسابات النهائية والتحقق من الخصم تتم على السيرفر.
- التكلفة وهامش الربح لا ينتقلان أبدًا إلى واجهة العميل.
- جميع التغييرات التجارية المهمة تسجل في Audit Log.
- يجب تصميم حالات الفشل والتحميل والحفظ قبل التنفيذ، وليس بعدها.
- تجربة الهاتف تركز على المراجعة والإرسال والمتابعة السريعة، بينما البناء المعقد للعروض يظل أفضل على الكمبيوتر.

## 29. سجل التنفيذ

### المرحلة الأولى — الأساس التجاري (8 أكتوبر 2026)

- إنشاء جداول D1 لقائمة الأسعار، تاريخ نسخ الأسعار، عروض الأسعار، نسخ العروض، بنود العروض، البرومو كود وسجل التدقيق.
- إضافة بيانات أولية لقائمة الأسعار الحالية بوحدة نقدية صحيحة `minor units`.
- إضافة API محمي داخل Studio لقراءة قائمة الأسعار وحفظ المسودة أو نشر التعديل.
- إضافة إنشاء البنود والباقات، إنشاء نسخة، الأرشفة والاستعادة بدون حذف التاريخ.
- ربط شاشة Price List بالـAPI مع وضع محلي بديل عند تشغيل Vite بدون Cloudflare Worker.
- التحقق من تطبيق جميع Migrations محليًا، ومن القراءة والإنشاء والحفظ والأرشفة والاستعادة وتسجيل رقم النسخة.
- ربط Quote Builder بإنشاء عرض حقيقي ورقم مرجعي تلقائي، وإنشاء إصدار جديد مع كل حفظ لاحق.
- نقل حساب الإجمالي والخصم والضريبة والتكلفة الداخلية إلى السيرفر، مع حفظ Snapshot مستقل لكل بند في كل إصدار.
- التحقق محليًا من عرض بإصدارين؛ تم حفظ نسختين وأربع لقطات بنود مستقلة بالقيم المحسوبة الصحيحة.
- إصدار رابط عميل آمن وفريد صالح لمدة 14 يومًا، مع إبطال الرابط السابق عند إعادة الإصدار.
- إنشاء صفحة عرض عامة مستقلة للعميل تدعم الإضافات الاختيارية والقبول وطلب التعديل.
- تسجيل أحداث الإرسال وأول مشاهدة والقبول وطلب التعديل، مع عدم إرسال التكلفة الداخلية أو هامش الربح إلى المتصفح العام.
- اختبار رحلة العميل كاملة محليًا: `sent → viewed → accepted` وتأكيد تسجيل كل حدث مرة واحدة.
- ربط غرفة التحكم بقائمة العروض الحقيقية وحالاتها وآخر نشاط وإجمالي العروض المفتوحة والهامش المتوقع.
- إضافة Telegram Alerts اختيارية لأحداث إرسال العرض وأول مشاهدة والقبول وطلب التعديل، مع حفظ المفاتيح كـCloudflare Secrets.
- نقل Promotions إلى D1 مع الإنشاء والجدولة والتفعيل والإيقاف وحد الاستخدام وتاريخ الصلاحية.
- جعل السيرفر هو المصدر الوحيد لقيمة الخصم؛ أي قيمة خصم يرسلها المتصفح بدون كود صالح يتم تجاهلها.
- اختبار كود `LAUNCH5` على إجمالي 10,000 جنيه؛ احتسب السيرفر 500 جنيه، بينما تجاهل محاولة خصم يدوي بقيمة 9,000 جنيه.
- ربط قسم الباقات بالموقع العام بـCatalog المنشور: الاسم والوصف والسعر والظهور والتمييز تتحدث من Studio، مع بقاء جميع تفاصيل المخرجات الحالية ظاهرة.
- إضافة Public Catalog API لا يكشف التكلفة الداخلية أو الحد الأدنى أو أي بيانات إدارية.
- إضافة شاشة Settings داخل Studio تعرض حالة Telegram وتسمح بإرسال رسالة اختبار دون عرض الأسرار.
- إضافة حقول Catalog للبنود المشمولة والمستبعدة ومدة التنفيذ وعدد المراجعات باللغتين.
- ربط تفاصيل الباقات الجديدة بالموقع العام مع Fallback يحافظ على كل التفاصيل الحالية حتى اكتمال نقل كل باقة.
- التحقق من أن التفاصيل تصل عبر Public API بينما تظل التكلفة الداخلية محجوبة.
- إضافة شاشة طلبات حقيقية داخل Commercial Studio وزر إنشاء عرض من كل Brief.
- نقل اسم العميل والمشروع والمرجع والميزانية والمدة والباقة المختارة تلقائيًا إلى Quote Builder وربط العرض بمعرف الطلب الأصلي.
- إضافة الباقة المطابقة من Catalog تلقائيًا كبند أول في العرض عند توفرها.
- تحويل العرض المقبول تلقائيًا إلى مشروع واحد مرتبط بالعرض، مع حفظ قيمة التعاقد والتكلفة والربح المتوقع.
- إنشاء دفعة مقدم وباقي رصيد تلقائيًا وفق نسبة المقدم في العرض.
- إضافة شاشتي Projects وPayments إلى Studio مع ملخصات مالية وإجراء تسجيل الدفعة كمُسددة وسجل تدقيق.
- تحديد استحقاق المقدم عند القبول وباقي الرصيد بعد 30 يومًا، وتصنيف الدفعات المتأخرة تلقائيًا.
- إضافة شاشة Reports لحساب التحويل وقيمة التعاقدات والربح المتوقع والتحصيل ومسار حالات العروض من البيانات الحقيقية.

الخطوة التالية: إضافة تنبيهات الدفعات المتأخرة المجدولة، ثم مراجعة النظام كاملًا قبل نقل البروتوتايب إلى Studio الإنتاجي.
