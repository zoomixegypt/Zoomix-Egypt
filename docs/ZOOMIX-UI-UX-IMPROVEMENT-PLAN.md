# ZOOMIX — UI / UX Improvement Plan

## 1. الهدف

تحويل موقع ZOOMIX من نسخة قوية بصريًا إلى تجربة واضحة وسريعة ومقنعة تساعد الزائر على:

1. فهم خدمات ZOOMIX بسرعة.
2. رؤية جودة الأعمال قبل اتخاذ قرار الشراء.
3. مقارنة الباقات بدون ارتباك.
4. إرسال Project Brief بسهولة من الموبايل والويب.
5. الوصول للمحتوى العربي والإنجليزي بطريقة قابلة للتوسع والـSEO.

هذا الملف هو خطة تطوير وتحسين، وليس قائمة تغييرات تم تنفيذها بالكامل.

---

## 2. الحالة الحالية

### تم تنفيذه بالفعل

- هوية Black / Lime / Off-white موحدة.
- دعم عربي / إنجليزي مع RTL / LTR.
- اللوجو الحقيقي داخل الـNavbar بدل النص.
- إصلاح ظهور اللوجو عند تغيير حجم الشاشة.
- تحسين تموضع الـHero على الموبايل.
- Mobile Menu.
- قسم خدمات واضح.
- قسم أعمال بثلاثة مشاريع Concept.
- صفحات مستقلة للمشاريع.
- باقات رسمية بالأسعار والمخرجات والمدد.
- Process وFAQ Accordion.
- Project Brief متصل بواتساب.
- Footer وروابط السوشيال ميديا.
- SEO أساسي وSitemap وRobots وJSON-LD.
- دعم Reduced Motion.
- Lazy Loading للأقسام الثانوية.
- `format:check` ناجح.
- `npm run build` ناجح.

### ما زال مقترحًا ولم ينفذ بعد

- إعادة ترتيب قسم الأعمال قبل الباقات.
- تطوير Project Modal من ناحية Accessibility والتنقل.
- تبسيط الـNavbar على الشاشات المتوسطة.
- إضافة توجيه واضح للسحب الأفقي في الأعمال.
- تبسيط نموذج التواصل على الموبايل.
- إضافة عناصر ثقة واقعية.
- تحسين SEO العربي والإنجليزي بشكل مستقل.
- اختبار Core Web Vitals بعد النشر.

## 4. خطة UI / UX الأساسية

## 4.1 إعادة ترتيب الصفحة

### الترتيب الحالي

```text
Hero
Services
Packages
Process
Work
Project Brief
Footer
```

### الترتيب المقترح

```text
Hero
Marquee
Services
Work
Packages
Process / FAQ
Project Brief
Footer
```

### السبب

الأعمال هي عنصر الثقة الأساسي لشركة Creative Partner، لذلك يجب أن يراها المستخدم قبل الأسعار.

### معيار النجاح

- يستطيع الزائر فهم الخدمة ثم رؤية مثال عليها قبل الوصول للباقات.
- يظهر CTA للأعمال في الـHero ويصل إلى القسم بسهولة.
- لا يحدث كسر في روابط الـNavbar أو الـFooter.

---

## 4.2 الـNavbar

### المشاكل المحتملة

- كثرة الروابط على الشاشات المتوسطة.
- احتمال اقتراب الروابط من CTA واللغة.
- بعض العناصر الثانوية تأخذ مساحة من العناصر المهمة.

### الاقتراح

الاحتفاظ بالروابط الأساسية:

- عن زومكس.
- الخدمات.
- الأعمال.
- تواصل.

ونقل:

- الباقات.
- طريقة العمل.

إلى Mobile Menu أو روابط داخل الصفحة فقط.

### تحسينات إضافية

- إضافة حالة Active للقسم الحالي.
- تقليل padding بين الروابط عند 1024–1280px.
- التأكد من عدم تغطية الـNavbar لعناوين الأقسام.
- الحفاظ على Safe Area في أجهزة iPhone.

### معيار النجاح

- لا يوجد تداخل عند 1024px و1280px.
- كل زر قابل للضغط بسهولة على اللمس.
- اللغة والـCTA يظلان ظاهرين.

---

## 4.3 الـHero

### ما يعمل جيدًا

- عنوان واضح.
- CTA مزدوج.
- Grid وهوية قوية.
- اللوجو ظاهر في الـNavbar.

### التحسينات المقترحة

- إبقاء CTA الأساسي أكثر وضوحًا من CTA الأعمال.
- استخدام اتجاه سهم مناسب للغة العربية.
- عدم استخدام tracking سالب قوي مع العناوين العربية.
- اختبار ارتفاع الـHero عند 375px و390px و430px.
- تجربة نسخة `85–90svh` على الموبايل إذا ثبت أن الـHero طويل.

### معيار النجاح

- العنوان لا يخرج من الشاشة.
- الأزرار لا تتداخل.
- CTA الأساسي يظهر بدون Scroll.
- لا يوجد فراغ غير مبرر أعلى أو أسفل المحتوى.

---

## 4.4 قسم الخدمات

### التحسينات المقترحة

- ربط كل خدمة بمثال من قسم الأعمال.
- إضافة CTA صغير تحت كل خدمة.
- تقليل النصوص الطويلة على الموبايل.
- استخدام أسماء ثابتة للخدمات في العربي والإنجليزي.

### معيار النجاح

بعد قراءة القسم يعرف المستخدم:

1. ماذا تقدم ZOOMIX.
2. لمن تناسب الخدمة.
3. أين يرى مثالًا عليها.

---

## 4.5 قسم الأعمال

### المشاكل الحالية

- الـHorizontal Scroll قد لا يكون واضحًا للجميع.
- البطاقات تعتمد على `role="button"` داخل عناصر غير Button.
- يجب دعم `Space` بجانب `Enter`.
- يحتاج المستخدم إلى معرفة أن هناك مشاريع إضافية.

### التحسينات المقترحة

- إضافة نص `اسحب للمزيد` أو `Scroll to explore`.
- إضافة أسهم السابق / التالي.
- جعل عداد المشاريع أوضح.
- إضافة Focus state واضح.
- دعم Enter وSpace.
- توفير fallback رأسي بسيط عند Reduced Motion.
- إضافة تسمية واضحة بأن المشاريع Concept عند الحاجة.

### معيار النجاح

- يستطيع المستخدم اكتشاف كل المشاريع بدون تخمين.
- تعمل البطاقات بالماوس واللمس والكيبورد.
- لا يعلق المستخدم داخل الـPinned Scroll.

---

## 4.6 Project Modal / Case Study

### التحسينات المطلوبة

- إضافة `aria-modal="true"`.
- نقل التركيز إلى أول عنصر داخل الـModal.
- منع خروج التركيز إلى الصفحة الخلفية.
- إعادة التركيز للبطاقة بعد الإغلاق.
- دعم Escape.
- إضافة زر Back to Work بجانب Close.
- إظهار أن المشروع Concept أو Directional Exploration.
- إضافة Project Navigation: السابق / التالي.
- تحديث Page Title حسب المشروع.
- التأكد من أن فتح Route مباشرة ثم الإغلاق يعيد المستخدم إلى الصفحة الرئيسية بشكل سليم.

### معيار النجاح

- كل Modal قابل للاستخدام بدون ماوس.
- لا يفقد المستخدم مكانه بعد الإغلاق.
- Refresh على Route المشروع يعمل.
- لا تظهر صفحة فارغة عند استخدام Back من Route مباشر.

---

## 4.7 الباقات

### ما يعمل جيدًا

- الأسعار واضحة.
- الباقة المقترحة مميزة.
- المدة والمخرجات والاستثناءات موجودة.
- الدفع واضح.

### التحسينات المقترحة

- إضافة جدول مقارنة مختصر.
- إظهار الفروقات الأساسية بين الباقات أولًا.
- جعل التفاصيل الطويلة داخل Accordion على الموبايل.
- توضيح لمن تناسب كل باقة في سطر مختصر.
- إبقاء زر الباقة ظاهرًا أثناء قراءة التفاصيل إن أمكن.

### معيار النجاح

- يستطيع العميل اختيار الباقة خلال أقل من دقيقة.
- يعرف ما هو مشمول وما هو منفصل.
- لا يحتاج للعودة بين أكثر من قسم لفهم الفرق.

---

## 4.8 Process وFAQ

### التحسينات المقترحة

- ربط كل مرحلة بمخرج واضح.
- تقليل المسافة الكبيرة قبل FAQ إذا ظهرت على الموبايل.
- إبقاء Accordion قابلًا للكيبورد.
- إضافة رابط من الإجابات المهمة إلى Project Brief.
- التأكد من أن الإجابة المفتوحة لا تغير مكان المستخدم بشكل مزعج.

---

## 4.9 Project Brief / WhatsApp

### المشاكل المحتملة

- النموذج طويل على الموبايل.
- كل البيانات تُجمع في صفحة واحدة.
- الاعتماد على فتح WhatsApp فقط قد يفشل بسبب Popup Blocker.

### الخطة المقترحة

#### خيار سريع

- الإبقاء على النموذج الحالي.
- تقليل الحقول الإجبارية إلى:
  - الاسم.
  - الهاتف.
  - نوع الخدمة.
  - وصف المشروع.

#### خيار أفضل

تقسيم النموذج إلى خطوات:

1. بيانات التواصل.
2. نوع المشروع والخدمة.
3. الباقة والميزانية.
4. الوصف والإرسال.

### إضافات مهمة

- استخدام `required` فعليًا.
- ربط رسائل الخطأ بالحقول.
- إظهار ملخص الرسالة قبل فتح WhatsApp.
- توفير زر نسخ الرسالة إذا فشل فتح WhatsApp.
- حفظ البيانات مؤقتًا أثناء الكتابة فقط إذا كان ذلك مطلوبًا.
- إضافة وقت الرد المتوقع.

### معيار النجاح

- يمكن إكمال النموذج بيد واحدة على الموبايل.
- المستخدم يفهم ماذا سيحدث بعد الإرسال.
- توجد خطة بديلة إذا لم يفتح WhatsApp.

## 5. Typography واللغة

### التحسينات المقترحة

- استخدام `tracking-normal` للعناوين العربية.
- استخدام line-height أعلى للعناوين العربية الطويلة.
- توحيد المصطلحات المختلطة مثل Brief وReels وLanding Page.
- جعل اتجاه الأسهم متوافقًا مع RTL / LTR.
- مراجعة الأرقام والأسعار في العربي والإنجليزي.
- اختبار 200% Text Zoom.

### معيار النجاح

- لا تتداخل الحروف العربية.
- لا تتقطع الكلمات.
- لا تتغير المسافات بشكل مزعج عند تبديل اللغة.

## 6. Responsive Testing Matrix

يجب اختبار الموقع على الأقل على المقاسات التالية:

| النوع | العرض | المطلوب |
|---|---:|---|
| Small mobile | 320px | لا يوجد قص أو Overflow |
| iPhone | 375px | Hero وForm واضحان |
| Large mobile | 430px | الكروت والأزرار متوازنة |
| Tablet portrait | 768px | لا يوجد Navbar collision |
| Tablet landscape | 1024px | انتقال صحيح بين Mobile وDesktop |
| Laptop | 1280px | Navbar وHero متوازنان |
| Desktop | 1440px+ | المساحات لا تبدو فارغة |

- اللوجو.
- Navbar.
- Hero.
- Marquee.
- Project cards.
- الباقات.
- FAQ.
- النموذج.
- الزر العائم.
- Footer.
- اللغة العربية والإنجليزية.

## 13. تعريف الجاهزية للنشر

لا تعتبر النسخة جاهزة للنشر إلا عند تحقق الآتي:

- لا يوجد تداخل في Desktop أو Mobile.
- اللوجو ظاهر في كل الحالات.
- كل CTA يعمل.
- كل مشروع يفتح ويغلق بشكل صحيح.
- Back وRefresh لا يؤديان إلى صفحة فارغة.
- النموذج يتحقق من الحقول ويرسل رسالة واضحة.
- واتساب يفتح أو يظهر fallback مناسب.
- العربي والإنجليزي يعملان.
- لا توجد أخطاء Console مؤثرة.
- `npm run format:check` ناجح.
- `npm run build` ناجح.
- تم اختبار Preview المنشور فعليًا.
